## 2. Current renderer capability map

| Capability | Current implementation | C-03 decision |
|---|---|---|
| Quest template | `evidence_hunt` only | Generate this template only |
| Scene registry | `school_library` only | Reject/avoid unknown scene IDs |
| Room/map layout | One fixed library map rendered with Phaser primitives | Not generated by C-03 |

| Document | `DOC-001`, fixed title and 3 paragraphs | `read_document.ref` must be `DOC-001` for current scene |

| Supported step types | `read_document`, `select_evidence` | No `talk_npc` or `make_inference` in public v1.0 |
| Learning paths | `needs_support`, `developing`, `ready_for_extension`; backend can also return `need_more_evidence` | Keep exactly three quest variant keys; do not invent a fourth variant |
| Reassessment | State machine can transition back to challenge/retry; current challenge uses the same item | Distinct reassessment item is not supported by current quest payload/scene content |
| Source references | LO analyzer carries PDF/DOCX source refs; Quest Schema has only `objective_ids` | Preserve provenance with persisted LO records; resolve from LO IDs server-side |

### Important runtime constraints

`prepareEvidenceHunt()` rejects a scene unless its steps reference the scene's current document and challenge item. `QuestFlow` prevents opening the challenge until the document was read. The current Phaser scene exposes NPC, document, and challenge hotspots, but their content comes from the static `SceneContent` object, not from the quest payload.

## 3. Answers to PIC D's C1–C8 questions

### C1. Can the generator emit valid JSON per `contracts/quest.schema.json` v1.0?

**Yes, for the currently registered capability set.** C-03 now includes `generateCompatibleQuestDraft()`, which emits the exact v1.0 root shape. An automated test has been added to pass the result through PIC D's `parseQuestV1()` and `prepareEvidenceHunt()`; an independent local runtime check has also verified both gates.

This implementation is a deterministic compatibility scaffold, not an AI narrative generator. It only targets `evidence_hunt` + `school_library` and the current `DOC-001`/`ITEM-001` references.

### C2. What is an actual example output?

The generated object has this shape (IDs and LO IDs are supplied by the backend):

```json
{
  "schema_version": "1.0",
  "quest_id": "QUEST-GENERATED-001",
  "quest_version_id": "QV-GENERATED-001",
  "objective_ids": ["LO-BAHASA-001"],
  "template": "evidence_hunt",
  "scene_id": "school_library",
  "steps": [
    { "id": "read-01", "type": "read_document", "ref": "DOC-001" },
    { "id": "evidence-01", "type": "select_evidence", "item_id": "ITEM-001" }
  ],
  "variants": {
    "needs_support": "QVAR-S",
    "developing": "QVAR-D",
    "ready_for_extension": "QVAR-E"
  }
}
```

The complete fixture remains a standard `{ ok, data, request_id }` response envelope when exposed publicly. Internal warning metadata is not part of this JSON.

### C3. Can the generator fill scene_id/template/steps?

**Yes, but only from the inspected allowlist.** `template` is `evidence_hunt`; `scene_id` is `school_library`; steps are the supported ordered pair `read_document(DOC-001)` then `select_evidence(ITEM-001)`. Quest and version IDs are supplied by backend orchestration. Objective IDs must be persistent, approved IDs supplied by PIC B after teacher review.

The generator must not invent scene IDs, document IDs, assessment item IDs, variant IDs, or LO IDs.

### C4. Will NPC/dialog content be in the current output, or handled by Story Adapter?

**It is not in Quest Schema v1.0.** The current NPC and dialog are local static scene content in `apps/web/src/game/sprint1/content.ts`. Keep that behavior in the game-side Story Adapter/local scene content for the current demo. C-03 must not add ad hoc root fields because the root schema sets `additionalProperties: false`.

Dynamic dialogue, documents, room layouts, and generated challenge prompts require a separate versioned content contract or a reviewed Quest Schema change agreed by B/A/C/D.

### C5. How are source references represented for NPC/object traceability?

Quest v1.0 has no source-reference field. C-02 already attaches source references to each Learning Objective. C-03 therefore retains only `objective_ids` in the quest. PIC B must persist the objective-to-source-reference relation and expose an authorized lookup if the game/teacher UI needs the provenance. Do not put PDF/DOCX source references into unapproved quest fields or assume an NPC/object can be traced to an LO without an explicit mapping contract.

### C6. Is there a validator and invalid-AI-output handling?

The C-03 scaffold validates required IDs, LO IDs, non-empty statements, and duplicate LO IDs before constructing a payload. Automated tests then use PIC D's `parseQuestV1()` and `prepareEvidenceHunt()` as compatibility gates. The repository's `npm run contract:lint` separately validates the public quest fixture against the authoritative JSON Schema.

There is no AI model output in this scaffold, so malformed-AI retry/fallback handling is not claimed as implemented. When a Gemini-backed content generator is added, it must use structured output, validate against the approved content contract, reject unsupported references, and return a typed error without silently patching invalid model output.

### C7. Can assessment and reassessment be distinct for the same LO?

**Not with the current payload/runtime contract.** The public quest payload contains only the `select_evidence` step and one `item_id` in the inspected scene. The state machine supports retry transitions, but current scene content reuses `ITEM-001`; it does not describe a second item or per-objective assessment mapping. A distinct reassessment requires an agreed item/variant schema and renderer support from D, plus backend scoring support from B.

### C8. Can the generator use fixtures without the production backend?

**Yes, for local compatibility tests.** The C-03 builder needs only a local input containing backend-shaped quest IDs and approved LO IDs. Unit tests run without Supabase, network access, or Gemini. The existing public quest fixture is also usable by PIC D's renderer. This scaffold does not prove the production API/job integration.

## 4. C-03 implementation boundary

PIC C currently owns:

- C-02 Learning Objective output as the source of learning intent;
- a deterministic Quest Schema v1.0 compatibility builder;
- validation of supplied IDs and objective inputs;
- local fixtures/tests and this integration note.

PIC B remains responsible for authentication, teacher approval persistence, persistent LO/quest IDs, quest-generation job/API lifecycle, and source-provenance persistence. PIC D remains responsible for game scene/renderer/Story Adapter support, item registry, assessment/reassessment mechanics, and the runtime contract. PIC A remains responsible for teacher review/approval UI.

## 5. Required decisions before AI-generated game content

1. PIC D provides/approves a registry of scene IDs, NPC IDs, object IDs, document slots, assessment item IDs, and supported interaction handlers.
2. PIC D defines the Story Adapter input shape and whether content is loaded separately from Quest Schema v1.0.
3. PIC B confirms the persistence/lookup shape for approved LO IDs and their PDF/DOCX source references.
4. PIC B/D define the assessment and reassessment item contract, including BedaJalur variants and server-side scoring ownership.
5. A/B/C/D approve a versioned content contract or formal CCR before any new public fields are added.

Until these are agreed, the compatibility scaffold is the maximum safe implementation: it proves structural and current-scene compatibility without claiming dynamic, material-specific gameplay.
